# 複雜變更方法論 (Complex Change Methodology)

## 何時啟用此框架

當變更符合以下任一條件時，應採用完整的複雜變更流程：

| 條件 | 說明 |
|------|------|
| **多檔案影響** | 預期修改 3 個以上檔案 |
| **核心模組** | 涉及 types.ts, services/, hooks/ |
| **介面變更** | 修改函數簽名或 Props 型別 |
| **資料流** | 變更狀態管理或 API 結構 |

---

## 四階段思考框架

### 階段 1：找入口 (Entry Point Discovery)
**目標**：確認變更的主要目標檔案

- 使用語意搜尋找出相關檔案
- 確認「Primary Target」(主要修改對象)
- 記錄入口點供後續追蹤

### 階段 2：評估半徑 (Impact Radius Assessment)
**目標**：了解變更的連鎖影響

- 分析 Dependencies (此檔案依賴誰)
- 分析 Dependents (誰依賴此檔案)
- 決定 Context 需包含的檔案範圍
- 📍 可使用 `npx tsx scripts/scan_impact.ts <target>` 自動分析

### 階段 3：TDD 開發 (Test-Driven Development)
**目標**：確保變更可驗證且無回歸

決策樹：
```
現有測試存在?
├── 是 → 先執行現有測試確認 baseline
└── 否 → 建立測試檔案

預期行為清晰?
├── 是 → 寫失敗測試 (Red)
└── 否 → 與使用者確認需求後再寫測試

實作完成?
├── 是 → 執行測試確認通過 (Green)
└── 否 → 持續迭代

有大量依賴者?
├── 是 → 執行相依模組測試
└── 否 → 執行 npm run test:run
```

### 階段 4：視覺驗證 (Visual Verification)
**目標**：確認 UI 呈現正確

- 啟動開發伺服器
- 使用 browser_subagent 進行自動化檢查
- 截圖記錄最終狀態

## 風險評估矩陣

| 變更類型 | 風險等級 | 建議作法 |
|---------|---------|---------|
| 樣式調整 | 🟢 低 | 直接修改 + 視覺驗證 |
| 新增功能 | 🟡 中 | TDD + 視覺驗證 |
| 重構現有功能 | 🟠 高 | 完整四階段 |
| 修改核心型別 | 🔴 極高 | 完整四階段 + 全面測試 |

---

## 快速判斷口訣

> **改一個，查三層：誰用它、它用誰、測試誰。**

1. **誰用它** (Dependents) - 避免破壞呼叫方
2. **它用誰** (Dependencies) - 確認基礎穩定
3. **測試誰** (Test Scope) - 決定驗證範圍
