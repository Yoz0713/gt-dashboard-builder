## Context

目前儀表板只有一條主資料流：使用者選擇單一試算表後，`useGoogleSheetData` 會載入該表的 `sheetData`，再用 `analyzeData` 產出 `analysisResult`，供總覽分析、區間比較與競賽排行共用。已儲存試算表在 `Controls` 內目前也只有單選行為，選到哪一份就直接覆蓋目前主畫面資料。

這次需求的衝突點在於競賽排行的資料範圍與其他兩個報表不同。總覽分析與區間比較仍然是「單一店別 / 單一試算表」的報表，但競賽排行要跨多個已儲存試算表加總同一個轉介門市在不同聽力中心的總轉介人次。如果繼續沿用同一份 `analysisResult`，就會把競賽的多試算表邏輯滲透到既有兩個區塊，回歸風險很高。

## Goals / Non-Goals

**Goals:**
- 讓競賽排行可複選多個已儲存試算表作為統計範圍
- 以所選試算表的來客紀錄做整併，依轉介門市加總總轉介人次
- 在總轉介人次之外，依 PTA 閾值拆分聽損客與正常客數
- 讓競賽排行沿用既有日期區間作為週期篩選條件
- 保持總覽分析與區間比較的單一試算表流程不變
- 以測試先行方式驗證多試算表整合與既有功能無回歸

**Non-Goals:**
- 不變更 Google Sheets 寫入方式或機器人權限模型
- 不新增資料庫或長期快取層
- 不在本次提案中設計距離加成、權重公式或最終競賽獎勵規則
- 不要求把總覽分析或區間比較改成多試算表分析
- 不在本次提案中新增新的後端批次 API

## Decisions

### 1. 競賽排行改走獨立資料流，避免污染既有 `analysisResult`
競賽排行會維持同一個頁面入口，但資料來源改為獨立狀態，例如 `selectedCompetitionSpreadsheetIds`、`competitionRankingEntries` 與對應的 loading / error 狀態。總覽分析與區間比較仍只依賴目前主試算表的 `sheetData` 與 `analysisResult`。

這個切法比「把多試算表整合後再塞回同一份 `analysisResult`」更安全，因為競賽排行的資料範圍、排序規則與欄位結構都與既有兩個區塊不同。替代方案會讓 `performAnalysis` 同時處理兩種不同來源範圍，後續維護成本更高。

### 2. 以平行抓取多份已儲存試算表資料，再在前端合併 `來客紀錄`
目前後端已提供單份已儲存試算表的讀取 API，且機器人帳號已在這些試算表授權範圍內。實作上可沿用既有 `/api/sheets/:id` 端點，以 `Promise.all` 平行抓取選定的試算表，再以第一份試算表的表頭為基準整併資料列，形成競賽排行專用的輸入資料。

替代方案是新增後端 batch API 一次回傳多份資料，但這會拉高此次變更範圍。只要在前端保留錯誤處理與選取數量限制（上限 10 份），現有 API 足以支撐這次需求。

### 3. 競賽排行以 `totalReferrals` 排序，但保留 PTA 分類明細
競賽規則描述的是「轉介門市在本週期總共成功轉介多少人到各聽力中心」，因此排行榜的主指標必須改成總轉介人次。分析時應將所有選定試算表中 `轉介門市` 有效值的資料列合併後，以轉介門市為 key 加總次數，產出類似 `rank`、`storeName`、`totalReferrals` 的結果。只有「轉介門市」欄位具有有效值（非空值、非 `#N/A`、非 `N/A`）的資料列才會被納入總轉介人次計算。

同時，因為使用者仍需要依 `PTA` 閾值區分聽損客與正常客，競賽排行輸出模型應額外包含 `hearingLossCustomers` 與 `normalCustomers`。聽損客的判定僅依聽力狀況：左耳或右耳 PTA 高於目前閾值者計為聽損客；雙耳皆未高於閾值者計為正常客，不考慮是否成交。若試算表缺少 PTA 欄位，或某筆資料列的 PTA 無法解析，該筆資料仍保留在總轉介人次內，並直接計入正常客。這兩個欄位不改變主排序依據，但提供競賽名單的結構化明細。

替代方案是完全移除 PTA 拆分，只保留總人次；但這會失去使用者想在競賽中同步觀察聽損 / 正常結構的需求。

### 4. 日期區間與 PTA 閾值都繼續沿用，但用途分離
競賽排行仍沿用主畫面目前的日期區間與 PTA 閾值。日期區間決定哪些資料列進入競賽週期；PTA 閾值則決定每筆門市轉介屬於聽損客或正常客（僅依聽力狀況判定，不考慮成交）。競賽名次本身仍以總轉介人次排序，避免分類欄位與名次規則混在一起。

替代方案是以聽損客數作為主排序條件，但那會偏離這次定義的「總轉介人次競賽」。

### 5. 競賽區塊新增專用複選，不取代現有單選主試算表
`Controls` 目前的「已儲存的試算表」單選會直接切換整個頁面主資料來源。新需求不應把競賽複選塞進主設定區，而是應在競賽排行 tab 內容內提供專用複選控制，例如多選清單或 checkbox list，並清楚標示該選取只影響競賽排行。選取數量上限為 10 份。

若目前的主試算表本身就存在於已儲存試算表清單中，競賽複選的初始狀態應預設選中該主試算表，讓使用者不必手動操作即可看到初步排行結果；若主試算表不是已儲存試算表的一員，則競賽複選不強制預選。

這比把原本單選直接改成複選，或把競賽複選放進主設定區更合理，因為前兩者都會讓總覽分析與區間比較失去既有的單一店別語意，並降低競賽專用操作的可理解性。

### 6. 表頭正規化策略
不同試算表的欄位名稱可能有差異（例如「轉介門市名稱」vs「轉介門市」）。實作上沿用現有 `analysis.ts` 中以 `header.includes()` 做模糊比對的方式來定位必要欄位。如果某份試算表缺少必要欄位（服務日期、轉介門市），則該試算表整份跳過，並在 UI 上顯示明確的錯誤提示，告知使用者哪份試算表無法被納入競賽。PTA 欄位不列為整份跳過條件；若缺失則其資料列直接計入正常客。

### 7. 測試分成聚合邏輯與頁面隔離兩層
分析層測試要覆蓋：
- 多份試算表中同一轉介門市的資料可正確加總
- 不同目標聽力中心的資料會併入同一轉介門市總數
- 同一轉介門市可依 PTA 閾值正確拆分聽損客與正常客（僅看聽力、不考慮成交）
- 缺少 PTA 欄位或 PTA 無法解析的資料列，仍會保留在總轉介人次內並計入正常客
- 日期區間可正確篩掉不在週期內的資料
- 同分時排序穩定
- 缺少服務日期或轉介門市欄位的試算表應被跳過且不影響其他試算表的聚合結果

UI 層測試要覆蓋：
- 競賽複選控制只會在競賽排行區塊中顯示，且可更新競賽排行
- 更動競賽複選不會覆蓋目前主試算表
- 總覽分析與區間比較在新控制加入後仍可正常切換與顯示
- 競賽複選初始狀態為主試算表已選中

## Risks / Trade-offs

- [選取的試算表欄位格式不完全一致] → 以 `header.includes()` 模糊比對做欄位定位，缺少必要欄位的試算表跳過並在 UI 提示
- [部分資料沒有 PTA，分類可能失真] → 將 PTA 缺失視為正常客並在規格中明確定義，避免整份試算表被排除
- [一次抓取多份試算表造成等待時間上升] → 使用平行請求並把 loading / error 限縮在競賽排行資料流，不阻塞既有報表；選取上限 10 份
- [使用者混淆主試算表與競賽複選範圍] → 將競賽複選放在競賽排行區塊內，並明確標示「此選取只影響競賽排行」
- [型別變更導致既有排行元件或測試失效] → 先補失敗測試，再調整型別與表格欄位，明確區分主排序欄位與 PTA 分類欄位
- [部分試算表讀取失敗讓整體排行不可信] → 對失敗來源明確顯示錯誤，避免默默產出不完整名次
