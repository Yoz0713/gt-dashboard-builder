## Context

目前前端在 `src/App.tsx` 以 tab 方式切換「總覽分析」與「區間比較」，分析資料則由 `useGoogleSheetData` 呼叫 `analyzeData` 後一次回傳整包 `analysisResult`。現有 `analysis.ts` 已經具備門市轉介分析雛形，但統計欄位偏向一般報表，尚未以競賽排行的人數規則輸出潛力客、非潛力客與排序後列表。

此變更屬於跨模組調整：需要擴充分析結果型別、調整資料彙總規則、並新增第三個 UI 視圖。由於現有門市轉介邏輯已可辨識來源與金額，最佳作法是延伸現有分析管線，而不是再做一條平行資料流程。

本次規劃採用 TDD。實作時應先以固定試算表樣本建立分析層測試，鎖定門市轉介篩選、潛力客/非潛力客統計與排序規則，再補 UI 層測試驗證 tab 切換與既有畫面仍可渲染。

## Goals / Non-Goals

**Goals:**
- 在既有分析結果中新增可直接渲染的 `competitionRankingAnalysis`
- 以既有 PTA 閾值與日期區間規則判定潛力客與非潛力客
- 新增第三個報表 tab，顯示依門市轉介彙總後的競賽排行
- 確保競賽排行與既有總覽、比較視圖使用同一批分析資料
- 以測試先行方式降低分析邏輯與既有報表回歸風險

**Non-Goals:**
- 不變更 Google Sheets 的資料寫入方式
- 不新增新的後端 API 或資料庫
- 不重新定義潛力客判斷規則
- 不在本次提案中處理營業額、成交率、額外獎勵機制、權重公式或多條件自訂排序

## Decisions

### 1. 延伸既有 `analyzeData` 輸出，而非另建新資料載入流程
競賽排行所需欄位都已存在於 `sheetData` 內，而且與總覽分析共用日期區間與 PTA 閾值。將邏輯集中在 `analyzeData` 可避免 UI 層重複計算，並確保多個報表的數字一致。

替代方案是讓新元件自行重跑資料彙總，但那會複製欄位解析、潛力客判斷與金額計算規則，增加後續維護風險。

### 2. 競賽排行改以轉介門市名稱欄位識別，補強輸出模型
競賽排行將不再依賴來源欄位是否包含「門市」，而是直接以轉介門市名稱欄位是否具有有效值作為門市轉介判定依據。這可避免把未填寫門市的資料歸入排行，也更貼近前端要顯示的實際分組鍵。輸出模型維持使用 `storeName`、`potentialCustomers`、`nonPotentialCustomers`、`rank`。

替代方案是同時檢查來源欄位與門市名稱欄位；但在排行需求中，真正需要的是可分組的門市名稱，因此以門市名稱欄位為主更準確。為兼容現況，實作仍可保留欄位名稱 fallback，但不再為空值建立「未填寫門市」分組。

### 3. 排序規則集中在分析層實作
排序規則為「潛力客數高者優先；潛力客數相同時，非潛力客數高者優先」。此規則應在分析層完成，UI 僅負責渲染排序結果。這可避免不同畫面或元件各自排序，造成名次不一致。

若潛力客數與非潛力客數都相同，實作上應加入穩定的第三排序條件，例如門市名稱字典序，以確保畫面穩定。

### 4. 以新元件承接第三個 tab，而非塞進既有圖表元件
競賽排行的資訊結構是「排序表格為主」，與 `AnalysisCharts`、`ComparisonView` 的用途不同。新增獨立元件可讓資料欄位、版面與未來匯出需求更容易維護。

### 5. 以分析層測試與畫面整合測試作為 TDD 主軸
測試將拆成兩層：
- 分析層：針對 `analyzeData` 建立樣本資料，先寫失敗測試，驗證只納入門市轉介、潛力客/非潛力客統計、排序與穩定順序。
- UI 層：針對 `App` 或新 tab 區塊補測試，驗證新增「競賽排行」後，總覽分析與區間比較仍可切換與顯示。

替代方案是只做手動驗證，但這無法有效保證原先功能正常，尤其分析結果是多視圖共用資料模型，回歸風險較高。

## Risks / Trade-offs

- [門市名稱來源仍有格式依賴] → 保留欄位名稱 fallback，但將空值視為非有效門市轉介，不建立「未填寫門市」分組
- [競賽排行與既有門市轉介統計可能出現定義差異] → 將潛力客判斷統一抽用既有 helper，避免雙軌規則
- [資料量變大時前端分析成本上升] → 競賽排行重用現有單次分析結果，不新增第二次全表掃描以外的重複處理
- [排序同分時畫面不穩定] → 在設計中加入穩定第三排序條件
- [既有功能被分析結果型別調整波及] → 先補回歸測試，再修改型別與 UI 切換邏輯

## Migration Plan

- 先建立 `Jest` 與 React Testing Library 測試基礎設施，讓 TDD 可落地執行
- 先補分析層與 UI 層的失敗測試，鎖定門市轉介排行與既有報表回歸條件
- 再擴充 `types.ts` 與 `analysis.ts` 的輸出模型與排序邏輯
- 接著新增競賽排行元件並接入 `App.tsx` tab 切換
- 最後執行測試與 build 流程，並以實際試算表手動確認排行結果與既有報表無回歸

- 是否需要在 UI 中額外顯示名次編號與同分規則說明
